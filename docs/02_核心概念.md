# 02 核心概念

> 在开始开发之前，理解这些核心概念会帮助你更快上手若茗 PaaS。

---

## 1. 租户（Tenant）

### 是什么

租户是若茗多租户体系的核心概念。可以把它理解为一个**独立的客户或组织**。

```
若茗 PaaS 平台
├── 租户 A（A 公司）
│   ├── 用户：张三、李四、王五
│   ├── 数据：A 公司的订单、客户、文档
│   └── 配置：A 公司的 AI 模型参数
├── 租户 B（B 公司）
│   ├── 用户：赵六、孙七
│   └── 数据：B 公司的订单、客户、文档（与 A 公司完全隔离）
└── 超级管理员（平台运营方）
    └── 可以管理所有租户，但有操作审计
```

### 关键特性

- **数据完全隔离**：租户 A 的数据绝对不会出现在租户 B 的查询结果里
- **自动注入**：通过 `core.multi_tenant.TenantAwareRepository` 基类，`tenant_id` 过滤自动生效，不需要开发者手动加条件
- **独立配置**：每个租户可以有自己的 AI 模型配置、功能开关、配额限制
- **平台公共模型**：`tenant_id=NULL` 的 AI 模型配置对所有租户可见，平台运营方可以配置共享模型
- **RLS 兜底防线**：即使应用层出 bug，PostgreSQL 行级安全策略（RLS）作为最后一道防线阻止跨租户数据泄漏
- **超管代入审计**：平台超级管理员可以"代入租户视角"操作，但所有代入操作强制审计，记录 before/after 快照

### 开发者需要知道的

```python
# ✅ 正确做法：继承 TenantAwareRepository，自动处理租户隔离
#    （位于 backend/app/core/base_repository.py:21）
class OrderRepository(TenantAwareRepository[Order]):
    pass

# ❌ 禁止：直接查全表，没有 tenant_id 过滤
orders = await db.execute(select(Order))  # 会查出所有租户的数据！

# ⚠️ 注意：所有业务表必须包含 tenant_id 字段
#       并且继承 BaseModel（已内置 tenant_id、软删除、乐观锁）
```

## 2. 模块（Module）

### 是什么

若茗的功能以**模块**为单位组织。每个模块是一个完整的功能域，包含自己的数据模型、业务逻辑、API 接口和前端页面。

### 模块分层（与代码实际实现对齐）

```
L0 核心框架（不可禁用，19项）
  └── app_factory / config / database / redis / exceptions / error_codes
      / response / security / sensitive_mask / middleware / logging
      / rate_limit / rate_limit_config / circuit_breaker / multi_tenant
      / base_model / base_repository / deps / celery_app / i18n
      这些是系统的"地基"，所有其他模块依赖它们

L1 基础服务（不可禁用，9项）
  └── auth / user / organization / permission / tenant / audit
      / system / config_center / dashboard
      企业应用的"标配"，任何 SaaS 产品都需要

L2 通用引擎（按需启用）
  └── event_bus / import_engine / export_engine / search
      / contact_sync 联系人同步治理 / workflow / state_machine

L3 通用模块（按需启用，7项）
  └── message 消息通知 / file_center 文件 / monitor 系统监控(含熔断器面板)
      / codegen 代码生成 / integration 集成中心
      / customer_order3 示例业务模块 / sso(规划中)

L4 高级能力（按需启用）
  └── feature_flag(规划中) / report_bi(规划中) / i18n / disaster_recovery(规划中) / compliance(规划中)

AI 模块（若茗核心差异化，8项已实现）
  └── llm 统一网关 / agent 单Agent编排 / conversation 对话上下文
      / knowledge 知识库RAG / prompt 版本化模板 / scene 场景路由
      / tool 工具注册中心 / feedback 对话反馈
  AI 模块（规划中）
  └── multi_agent 多工作流编排 / eval 模型评测
```

### 如何添加你的业务模块

你的业务代码放在 `backend/app/modules/` 下，作为独立模块。详见 [如何添加业务模块.md](./如何添加业务模块.md)。

## 3. 权限（Permission）

### 模型概览

若茗采用 **RBAC（基于角色的访问控制）+ 角色继承** 模型，精细度到**按钮和表格列**级别。

```
用户（User）
  └── 拥有多个角色（Role）
        └── 角色继承（子角色自动继承父角色权限）
              └── 包含多个权限项（Permission）
                    ├── 菜单权限：能看到哪些菜单
                    ├── 接口权限：能调用哪些 API
                    ├── 按钮权限：页面上哪些按钮可见/可点
                    └── 数据权限：能看到哪些范围的数据
```

### 权限标识符规范

```
{模块}.{资源}.{操作}

示例：
  order.list.view        查看订单列表
  order.detail.export    导出订单详情
  user.password.reset    重置用户密码
  report.finance.view    查看财务报表
```

### 开发者使用方式

```python
# 后端：接口添加权限校验
@router.get("/orders")
@require_permission("order.list.view")
async def list_orders(...):
    ...

# 前端：按钮根据权限显示
<el-button v-if="hasPermission('order.detail.export')">
  导出
</el-button>
```

## 4. AI Agent

### 是什么

Agent 是若茗 AI 模块的核心单元。一个 Agent 代表一个**具有特定能力和行为的 AI 助手**。所有 Agent 的 LLM 调用必须经过**统一 LLM 网关**（`ai.llm.service.LLMService`），该网关提供协议适配、熔断降级、语义缓存、Token 计量等能力，**禁止业务代码直接调 LLM SDK**。

```
Agent 配置
├── 基本信息：名称、描述、图标
├── 模型配置（实际经过 LLM Gateway 路由）
│   ├── protocol: openai_compat / anthropic / gemini 三协议原生支持
│   ├── provider: 追鹿(默认主力) / OpenAI / DeepSeek / Qwen / 追鹿 / Ollama 等
│   ├── 模型: claude-sonnet-4 / gpt-4o / gemini-2.5-pro ...
│   └── 参数: temperature、max_tokens
├── System Prompt：AI 的角色设定和行为准则
├── 工具列表：Agent 可以调用哪些工具（搜索、代码执行沙箱、HTTP API、数据库查询、文件处理、数据分析）
├── 知识库：关联哪些知识库（用于 RAG 检索）
├── 场景配置：不同场景（闲聊/专业/任务/RAG/创意）使用不同参数
├── 会话配置：记忆多少轮对话历史
└── 安全机制：所有 LLM 调用透明经过 ①三状态熔断器 ②语义缓存 ③Token 计量 ④调用日志
```

```
LLM Gateway 调用路径（开发者通常不感知）
┌───────────────────────────────────────────────────────┐
│  AgentExecutor 执行器（AST 解析 + 多轮上下文管理）         │
└────────────┬──────────────────────────────────────────┘
             │
┌────────────▼──────────────────────────────────────────┐
│  LLMService.chat() / stream_chat()                     │
│   ├── ① 熔断器状态检查：CLOSED → OPEN(熔断) → HALF_OPEN │
│   │     └── OPEN 时自动切换 is_fallback 备用模型        │
│   ├── ② 语义缓存命中？temperature=0 且相同请求 → 直接返回 │
│   ├── ③ 路由到具体 Provider：Zhuilu / OpenAICompat    │
│   │                         / Anthropic / Gemini       │
│   ├── ④ 调用 + 写入 ai_call_log（Token/延迟/状态）     │
│   └── ⑤ 成功 → 重置熔断器 / 失败 → 累加失败计数         │
└────────────┬──────────────────────────────────────────┘
             ▼
   多协议 Provider (Zhuilu / OpenAI / Anthropic / Gemini / Ollama)
```

### 使用方式

```python
# 调用 Agent
POST /api/v1/ai/agent/{agent_id}/run
{
    "message": "帮我分析这份合同的风险条款",
    "session_id": "user-session-123",
    "scene_type": "professional",     # 可选，不传则自动路由
    "has_attachment": false
}
```

### 场景路由

同一个 Agent 会根据消息内容自动切换场景：

```
用户消息
    ↓
① 前端显式传入 scene_type（最准确）
② Agent 绑定的默认场景
③ 规则引擎推断（关键词 + 消息长度）
④ 轻量模型分类（可选，有成本）
⑤ 兜底：professional
    ↓
加载场景对应的 Prompt + temperature + 模型
    ↓
执行推理
```

## 5. 知识库（Knowledge Base）

### 是什么

知识库是若茗 RAG（检索增强生成）能力的数据来源。你可以上传各种文档，Agent 在回答时会从中检索相关内容。

```
知识库
├── 文档列表
│   ├── 合同模板.pdf      → 解析 → 分块 → 向量化 → 存入向量库
│   ├── 产品说明书.docx   → 解析 → 分块 → 向量化 → 存入向量库
│   └── 常见问题.txt      → 解析 → 分块 → 向量化 → 存入向量库
└── 检索配置
    ├── 向量检索（语义相似）
    ├── BM25 全文检索（关键词匹配）
    └── RRF 融合排序 + Rerank 精排
```

### 支持的文档格式

PDF、Word（docx）、Excel（xlsx）、Markdown、TXT、HTML、CSV

## 6. 配置中心（Config Center）

### 是什么

配置中心管理系统中所有可动态调整的配置项，支持**四级覆盖**，无需重启服务即可生效。

### 四级优先级

```
全局默认（Global）
    ↓ 被覆盖
租户配置（Tenant）  ← 租户管理员可以设置
    ↓ 被覆盖
应用配置（App）    ← 特定功能模块的配置
    ↓ 被覆盖
用户配置（User）   ← 用户个人偏好
```

### 典型使用场景

```python
# 读取配置（自动按优先级合并）
config = await config_center.get(
    key="ai.default_temperature",
    tenant_id=current_tenant_id,
    user_id=current_user_id,
)
# 如果用户设置了 temperature=0.5，就用 0.5
# 否则用租户配置，否则用全局默认值
```

## 7. 事件总线（Event Bus）

### 是什么

事件总线是若茗实现**模块间解耦**的核心机制。模块之间通过发布/订阅事件通信，而不是直接调用。

```
用户注册成功
    ↓ 发布事件 UserRegistered
    ├── 认证模块：发送欢迎邮件
    ├── 租户模块：初始化租户配额
    └── 审计模块：记录注册日志

以上三个模块各自独立监听，互不知晓对方存在
```

### 特性

- **持久化**：事件存储到数据库，不会因为进程崩溃而丢失
- **重试**：消费失败自动重试，支持指数退避
- **死信队列**：超过重试次数的事件进入死信队列，人工处理
- **延迟事件**：支持"5 分钟后触发"的延迟事件

## 8. 操作审计（Audit Log）

### 是什么

若茗自动记录所有写操作（增删改）的完整日志，包含**变更前后数据快照**。

```
日志记录内容：
├── 操作人（用户 ID、用户名、IP）
├── 操作时间
├── 操作类型（CREATE / UPDATE / DELETE）
├── 操作对象（模块、资源类型、资源 ID）
├── 变更前数据（before_data）
└── 变更后数据（after_data）
```

### 开发者使用方式

```python
# 方式一：装饰器（推荐）
@audit_log(action="UPDATE", resource="order")
async def update_order(order_id: int, data: OrderUpdate):
    ...

# 方式二：手动记录
await audit_service.log(
    action="EXPORT",
    resource_type="order",
    description="导出订单数据 500 条",
)
```

## 9. 多环境配置

若茗区分三个运行环境，通过 `APP_ENV` 环境变量切换：

| 环境 | 用途 | 配置文件 |
|------|------|---------|
| `development` | 本地开发 | `.env.development` |
| `test` | 自动化测试 / CI | `.env.test` |
| `production` | 生产部署 | 通过 CI Secret 注入，不落磁盘 |

**关键原则**：
- 生产环境配置绝对不提交到 Git
- `DATABASE_URL` 和 `SECRET_KEY` 未配置时，应用启动即报错（Fail-Fast）

## 10. 三状态熔断器（Circuit Breaker）

### 是什么

若茗在 L0 框架层实现了通用熔断器，目前核心应用于** LLM 调用**场景，防止某个模型/供应商故障时造成请求雪崩或大面积超时。管理员可以在**系统监控 → LLM 熔断器面板**查看状态和手动干预。

### 三状态状态机

```
                连续失败达到 failure_threshold (默认 5 次)
   ┌─────────┐ ─────────────────────────────────────────▶ ┌────────┐
   │ CLOSED  │                                            │  OPEN  │
   │ 正常调用 │                                            │ 熔断！ │
   │ 成功→重置│ ◀───────────────────────────────────────── │ 禁止调 │
   └─────────┘   等待 reset_timeout 秒 (默认 60 秒)        └────┬───┘
        ▲                                                      │
        │                 1 个探测请求通过                      │
        │                                                      ▼
        │                                            ┌─────────────┐
        │                                            │ HALF_OPEN   │
        └─────────────────────────────────────────── │ 半开/探测   │
                     探测成功 → 恢复 CLOSED            │ 放行少量请求│
                     探测仍失败 → 回到 OPEN            └─────────────┘
```

### 关键参数（可通过配置中心调整）

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `failure_threshold` | 5 | 连续多少次失败后熔断 |
| `reset_timeout` | 60 秒 | OPEN → HALF_OPEN 的冷却时间 |
| `success_threshold` | 2 | HALF_OPEN 需要连续成功多少次才恢复 |

### 与 LLM 网关的联动

- **每个 LLM 模型（model_id）独立一个熔断器**：不会因为追鹿故障把 Qwen 也熔断
- **`is_fallback=True` 的备用模型自动兜底**：主模型熔断时，LLMService 自动切到该租户的备用模型，对调用方透明
- **管理面板可视化**：monitor 模块提供实时状态、手动打开/关闭、重置计数器

## 11. LLM 语义缓存（Semantic Cache）

### 是什么

针对"同一问题反复提问"的场景（客服 FAQ、用户重复刷新、同类参数），将 LLM 调用结果存入 Redis Hash，**命中时直接跳过 LLM 调用**，降低 30%~80% 的 Token 成本和延迟。开发者调用 LLMService 时默认生效，无需手动处理。

### 缓存 Key 生成规则

```
Key = redis_hash(
    model_id + "::" +
    hash_sha256(json.dumps(messages, sort_keys=True)) + "::" +
    temperature + "::" +
    max_tokens
)
Field = tenant_id
Value = {'answer': '...', 'usage': {'prompt_tokens': 0, 'completion_tokens': 0}}
TTL  = 24 小时（可通过配置中心 llm.cache.ttl_seconds 调整）
```

### 何时命中、何时穿透

| 条件 | 行为 |
|------|------|
| `temperature == 0` 且 Key + Field 命中 | ✅ 直接从 Redis 返回，`llm_cache_hit=1` 写入日志 |
| `temperature != 0` | ❌ 不缓存（随机性请求不保证一致答案） |
| 缓存不存在 | ❌ 正常调用 LLM，成功后异步回填缓存 |
| 缓存已过期 | ❌ 正常调用 LLM，成功后异步回填缓存 |

## 12. 关键名词速查

| 名词 | 含义 |
|------|------|
| `TenantAwareRepository` | 自动注入 tenant_id 的数据库访问基类（`base_repository.py:21`） |
| `BaseModel` | 所有数据模型的基类（id/时间戳/软删除/租户字段）|
| `ApiResponse` | 统一响应格式封装 |
| `RequestID` | 每个请求的唯一标识，贯穿日志全链路 |
| `LLM Gateway` | 统一的大模型调用入口，屏蔽追鹿/OpenAI兼容/Anthropic原生/Gemini原生 四种协议差异，内置熔断、缓存、计量 |
| `Circuit Breaker` | 三状态熔断器（CLOSED→OPEN→HALF_OPEN），LLM 调用故障时自动切换备用模型 |
| `Semantic Cache` | LLM 语义缓存，基于 Redis Hash 按 model+messages 哈希命中，减少重复调用成本 |
| `SensitiveMask` | 敏感字段自动脱敏（手机号/邮箱/身份证/API Key/Token），日志与响应双重处理 |
| `RLS (Row Level Security)` | PostgreSQL 行级安全，应用层之下的最后一道租户隔离防线 |
| `RAG` | 检索增强生成，先检索知识库再让 AI 回答 |
| `SSE` | Server-Sent Events，AI 流式输出的传输协议 |
| `Celery` | 异步任务队列（调度 cronjob、知识库解析、集成 webhook 同步等实际使用）|
| `Alembic` | 数据库迁移工具，管理表结构变更历史 |
| `Pydantic v2` | 请求/响应数据验证库 |
| `AST Executor` | Agent 内的代码工具执行器，通过 `ast.parse` 静态安全检查后运行受限 Python |
| `Scene Router` | 5 级场景路由链（显式→默认→规则→模型→兜底），自动选择 agent 温度和 prompt |
| `Config Center` | 四级配置覆盖（全局→租户→应用→用户），热更新无需重启 |
