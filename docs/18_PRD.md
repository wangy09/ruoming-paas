## 1. 产品概述

### 1.1 产品定位

若茗 PaaS（RuoMing PaaS）是一套**面向专业开发者的企业级 AI 应用开发底座**。

它不是可以直接销售给最终用户的 SaaS 软件，而是帮助**开发团队**跳过重复造基础设施的阶段，直接在一个生产可用的底座上构建自己的企业应用或 SaaS 产品。

**一句话定位**：企业级底座 + 原生 AI 能力，开发者只写业务代码。

### 1.2 产品目标

| 目标层次 | 描述 |
|---------|------|
| **用户目标** | 开发者使用若茗后，基础设施搭建时间从 10-20 周缩短至 0（开箱即用），专注业务开发 |
| **业务目标** | v2.0 MVP 阶段吸引首批种子开发者使用，收集真实反馈，形成可持续改进闭环 |
| **技术目标** | 生产可用（非 Demo 级别）：每项设计决策都考虑安全性、稳定性、可扩展性 |

### 1.3 核心价值主张

```
对比维度        若茗 PaaS               竞品现状
─────────────────────────────────────────────────────
AI + 企业底座  两者二合一，原生集成      Dify 有 AI 无企业底座
                                         RuoYi 有企业底座无 AI
多租户         行级隔离，自动注入        大多数框架需自己实现
权限粒度       细粒度到按钮/列级         大多数框架只到菜单级
生产可用       安全基线、熔断、审计内置   Boilerplate 模板无这些
技术栈         FastAPI + Vue3（现代）    RuoYi 是 Spring Boot + Vue2/3
```

## 2. 用户画像（Persona）

### Persona A：独立开发者 / 小团队 Lead

| 属性 | 描述 |
|------|------|
| **典型背景** | 1-5 人团队，Python + Vue 技术栈，接外包或自做 SaaS 产品 |
| **核心痛点** | 每个项目都要从头搭权限、多租户、日志，消耗大量时间 |
| **核心诉求** | `docker-compose up` 就能跑，文档清晰，会用 FastAPI 就能上手 |
| **次要诉求** | 代码结构规范，方便后期维护；有 AI 能力可以快速实现 AI 功能 |
| **使用场景** | 用若茗接外包项目；在若茗上开发自己的 AI SaaS |
| **成功标准** | 1 天内本地跑通，1 周内在底座上写出第一个业务模块 |

### Persona B：中小企业研发 Lead

| 属性 | 描述 |
|------|------|
| **典型背景** | 5-20 人团队，需要给企业客户交付内部系统（CRM/OA/审批）|
| **核心痛点** | 客户要求有权限审计、安全合规、日志留存，自己实现成本高 |
| **核心诉求** | 安全基线满足客户要求，多租户支持多个企业客户，权限满足合规 |
| **次要诉求** | 代码可维护性高，团队成员上手快，有完整文档 |
| **使用场景** | 用若茗交付多个企业客户的系统，底层基础设施复用 |
| **成功标准** | 满足客户提出的安全/审计要求，无需另外花时间实现 |

### Persona C：AI 产品创业者

| 属性 | 描述 |
|------|------|
| **典型背景** | 想做企业级 AI 产品（AI 合同分析、AI 客服、AI 知识管理），技术背景较强 |
| **核心痛点** | 既要搞 AI 能力又要搞企业级功能，人力不够 |
| **核心诉求** | AI Agent、RAG、多租户开箱即用；每个租户可独立配置 AI 参数 |
| **次要诉求** | Token 配额控制（控成本）；Prompt 版本化（迭代 AI 能力不影响线上）|
| **使用场景** | 在若茗上构建垂直 AI SaaS，快速 MVP 验证 |
| **成功标准** | 2 周内跑通 AI Agent + RAG 流程，可对外演示 |

## 3. 功能范围与优先级

> 使用 MoSCoW 方法划分优先级：  
> **M（Must）**= MVP 必须有；**S（Should）**= v3.0 应有；**C（Could）**= 有更好；**W（Won't）**= 当前版本不做

### 3.1 认证与用户管理

| # | 功能 | 优先级 | 验收标准 |
|---|------|--------|---------|
| 1.1 | 用户名/密码登录，JWT 颁发 + Refresh Token 轮换 | **M** | 登录成功返回 Access Token（15 分钟）+ Refresh Token（7 天）；Refresh Token 使用一次后自动轮换 |
| 1.2 | 用户注册（平台超管创建 / 邀请链接注册） | **M** | 超管可创建用户并分配租户和角色 |
| 1.3 | 连续登录失败 5 次锁定账号 30 分钟 | **M** | 第 5 次失败后返回锁定错误，30 分钟后自动解锁 |
| 1.4 | API Key 管理（三方系统调用） | **M** | 超管可生成/撤销 API Key；API Key 请求经过相同权限校验 |
| 1.5 | 个人资料修改（头像、密码、手机号） | **S** | 修改密码需要验证旧密码；修改手机号需短信验证码 |
| 1.6 | SSO 集成：企业微信 / 钉钉 / OIDC | **S** | 配置 OAuth 参数后可通过企微/钉钉扫码登录 |
| 1.7 | 登录日志查询（时间/IP/设备） | **S** | 管理员可查询指定用户的最近 90 天登录记录 |
| 1.8 | 双因素认证（TOTP） | **C** | — |
| 1.9 | 手机号/邮箱验证码登录 | **C** | — |

### 3.2 权限系统

| # | 功能 | 优先级 | 验收标准 |
|---|------|--------|---------|
| 2.1 | RBAC 角色管理（角色增删改查） | **M** | 可定义角色，角色绑定权限节点 |
| 2.2 | 角色继承（子角色继承父角色权限） | **M** | A 继承 B，A 自动拥有 B 的所有权限，继承链支持多级 |
| 2.3 | 菜单级权限控制 | **M** | 无菜单权限的用户无法看到对应菜单项 |
| 2.4 | 按钮/操作级权限控制 | **M** | 接口层校验权限标识，无权限返回 403；前端隐藏对应按钮 |
| 2.5 | 表格列级权限控制 | **S** | 数据列按权限过滤返回，无权限列不出现在响应中 |
| 2.6 | 数据行级权限（按部门/创建人） | **S** | 支持"仅查看本人数据"和"仅查看本部门数据"两种模式 |
| 2.7 | 权限元数据前后端同步 | **M** | 前端菜单/按钮由后端权限数据驱动，安全校验在后端 |

### 3.3 多租户

| # | 功能 | 优先级 | 验收标准 |
|---|------|--------|---------|
| 3.1 | 租户注册与审核（平台超管审核） | **M** | 提交租户注册申请 → 超管审核通过 → 租户激活 |
| 3.2 | 数据行级隔离（TenantAwareRepository） | **M** | 任何 API 无法查询到其他租户的数据；Repository 自动注入 tenant_id |
| 3.3 | 配额管理（用户数/存储/API 调用/AI Token） | **M** | 超出配额时 API 返回 429，AI Token 超配额实时拒绝 |
| 3.4 | 租户套餐（basic/pro/enterprise） | **S** | 不同套餐对应不同配额上限，可升级套餐 |
| 3.5 | 租户个性化配置（主题色/Logo） | **C** | — |
| 3.6 | 独立实例部署模式（dedicated）| **C** | — |

### 3.4 配置中心

| # | 功能 | 优先级 | 验收标准 |
|---|------|--------|---------|
| 4.1 | 四级分层配置（全局→租户→应用→用户）| **M** | 低级配置覆盖高级，未设置时向上继承 |

| # | 功能 | 优先级 | 验收标准 |

| 5.2 | 登录日志（成功/失败/IP） | **M** | 每次登录事件记录，含 IP/设备/UA |

## 4. 非功能性需求

### 4.1 性能基线

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 普通 API 接口响应时间（P95） | ≤ 200ms | 不含 LLM 调用的业务接口 |
| 登录接口响应时间（P95） | ≤ 300ms | 含 bcrypt 密码校验 |
| LLM 同步调用等待超时 | ≤ 30s | 超时返回错误，不无限等待 |
| LLM 异步任务返回 task_id | ≤ 100ms | POST 立即返回，不等待 LLM |
| 数据导入（百万行 Excel） | ≤ 10 分钟 | 异步后台任务处理 |
| 数据导出（百万行）| ≤ 5 分钟 | 流式写入，内存占用 ≤ 512MB |
| 并发用户数（单实例） | ≥ 500 | 普通业务接口，不含 AI 请求 |

### 4.2 可用性

| 指标 | 目标值 |
|------|--------|
| 服务可用性 SLA | ≥ 99.5%（月度）|
| 单次故障恢复时间（MTTR） | ≤ 15 分钟（含告警响应）|
| AI 网关熔断后降级时间 | ≤ 5 秒（切换备用模型）|

### 4.3 安全要求

| 安全项 | 要求 |
|--------|------|
| 认证 | JWT Access Token 有效期 ≤ 15 分钟；Refresh Token Rotation |
| 密码存储 | bcrypt 单向哈希，禁止明文存储 |
| 敏感配置 | API Key / DB 密码 AES-256 加密后存储 |
| SQL 注入 | 全程 ORM 参数化查询，禁止字符串拼接 SQL |
| 跨租户防护 | Repository 层 tenant_id 注入 + 兜底拦截双重检查 |
| 文件上传 | MIME + 文件头 magic bytes 双重检测，白名单扩展名 |
| 爆破防护 | 登录失败 5 次锁定，IP 限流 |
| 日志安全 | 日志中不出现密码/Token 明文；（Phase 2）手机号/邮箱自动 mask |

### 4.4 可维护性

| 维度 | 要求 |
|------|------|
| 代码覆盖率 | L0/L1 核心模块 API 层测试覆盖率 ≥ 80% |
| 文档 | 每个公开 API 接口有 Swagger 文档描述；每个模块有对应设计文档 |
| 数据库迁移 | 所有 Schema 变更通过 Alembic 管理，禁止手动改表 |
| 配置校验 | 启动时 Fail-Fast 校验所有必要环境变量，缺失立即报错退出 |
| 日志 | 关键操作必须有结构化日志，含 RequestID / tenant_id / user_id |

### 4.5 兼容性

| 维度 | 要求 |
|------|------|
| Python 版本 | ≥ 3.11 |
| PostgreSQL 版本 | ≥ 15 |
| Redis 版本 | ≥ 7.0 |
| 浏览器兼容 | Chrome 最新版、Firefox 最新版、Edge 最新版（不支持 IE）|
| 移动端 | 响应式布局，管理后台在平板（768px+）可正常使用 |

## 5. 用户故事（核心主干流程）

### Story 1：开发者首次使用若茗

```
作为一名独立开发者，
我想通过 docker-compose up -d 在 10 分钟内跑起若茗底座，
以便验证若茗是否适合我的项目。

验收标准：
- clone 代码后，按 README 步骤，15 分钟内完成本地启动
- 能访问前端页面（http://localhost:3000），使用默认账号 admin/ruoming@2024 登录
- 能访问 API 文档（http://localhost:8000/api/docs）
- 首次启动自动完成数据库初始化（表结构 + 种子数据）
```

### Story 2：开发者添加第一个业务模块

```
作为底座开发者，
我想按照规范添加一个业务模块（如"工单管理"），
让底层的权限、多租户、审计能力自动生效，无需重复实现。

验收标准：
- 参照《如何添加业务模块.md》，1 天内完成一个完整 CRUD 模块
- 继承 TenantAwareRepository，多租户隔离自动工作，无需额外代码
- 使用 @audit_log 装饰器，操作日志自动记录
- 在权限管理界面配置权限后，接口和前端按钮权限控制自动生效
```

### Story 3：租户管理员管理用户

```
作为租户管理员，
我想管理我租户下的用户（创建/禁用/分配角色），
以便控制谁能访问哪些功能。

验收标准：
- 可创建新用户并分配角色
- 可禁用用户（禁用后立即无法登录，已有 Token 失效）
- 可查看本租户所有用户的登录记录
- 操作严格限制在本租户范围内，无法看到其他租户数据
```

### Story 4：AI 产品开发者接入 Agent

```
作为 AI 产品开发者，
我想定义一个客服 Agent（绑定知识库 + Prompt 模板），
并通过 API 调用 Agent 回答用户问题，
以便快速搭建 AI 客服功能。

验收标准：
- 在管理后台创建 Agent，配置系统 Prompt、绑定知识库、选择模型
- 调用 /api/v1/ai/agent/{agent_id}/run，传入用户问题，返回 AI 回答
- 知识库中的文档内容被正确检索并注入 Prompt
- 每次 AI 调用记录到 ai_call_log（含 token 消耗）
- 当天 Token 超过租户配额时，接口返回 429 并提示配额已用尽
```

### Story 5：平台超管监控系统状态

```
作为平台超管，
我想查看所有租户的 API 调用量和 AI Token 消耗，
以便了解资源使用情况并处理异常租户。

验收标准：
- 可查看每个租户的当日 API 调用次数和 AI Token 消耗
- 可查看近 7 天的用量趋势图
- 可手动禁用超出合理范围的租户
- 系统异常（如某租户异常高频调用）有告警提示
```

## 7. 约束与假设

### 技术约束

| 约束 | 说明 |
|------|------|
| 语言 / 框架锁定 | 后端 Python 3.11+ / FastAPI；前端 Vue3 + TypeScript。不支持 Java/Go/React 替代 |
| 数据库锁定 | 核心功能依赖 PostgreSQL（RLS、pgvector、JSONB），不支持 MySQL 替代 |
| LLM 接入 | 以追鹿 API 为主力，OpenAI 兼容层作备用；不直接依赖 OpenAI SDK |

### 产品边界（不在范围内）

| 功能 | 说明 |
|------|------|
| 最终用户界面 | 若茗是开发底座，不提供面向最终业务用户的前端界面；管理后台仅面向开发者/管理员 |
| 低代码搭建 | 不做拖拉拽搭建能力（Dify 路线），若茗是开发者代码框架 |
| 插件市场 | v4.0 规划，v1.0-v3.0 不做 |
| 多云适配层 | 若茗是底座，用户自选部署环境；已有抽象接口（如 VectorStoreAdapter）处理可替换组件 |
| 服务注册发现 | Nginx 已满足；K8s 环境下 Service 天然解决；不引入 Consul/Nacos |

### 假设

1. 目标用户能够自行操作 Docker 和命令行
2. 部署环境可以访问追鹿 API 或 OpenAI 兼容接口
3. MVP 阶段向量库使用 pgvector（与主库同实例），无需单独部署 Milvus
