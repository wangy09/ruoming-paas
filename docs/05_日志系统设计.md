# 05 日志系统设计

## 1. 日志分类体系

| 日志类型 | 说明 | 存储位置 | 保留期 |
|---------|------|---------|--------|
| 访问日志 | 每次 HTTP 请求（方法/路径/状态码/耗时） | 文件 | 30 天 |
| 错误日志 | ERROR 及以上级别单独归档 | 文件 | 30 天 |
| 操作日志（审计） | 敏感资源的写操作 + 部分读操作，含变更快照 | 数据库 `sys_audit_log` | 长期 |
| 登录日志 | 登录/登出/失败记录 | 数据库 `sys_login_log` | 长期 |
| 系统日志 | 程序运行状态、启动/关闭、异常 | 文件（含访问日志） | 30 天 |
| AI 调用日志 | LLM 调用记录（Token 用量/延迟/费用估算） | 数据库 `ai_call_log` | 90 天 |
| 前端接口错误 | 浏览器侧接口报错快照（仅当前会话内存） | 前端内存（最多 200 条） | 页面关闭即清空 |

## 2. 后端日志引擎架构

项目采用 **双引擎协作** 方案：

```
业务代码
  └─ structlog.get_logger()          ← 统一调用入口
       │
       ├─ 结构化处理（contextvars 绑定 trace_id/user_id/tenant_id）
       ├─ 开发环境：ConsoleRenderer（彩色可读）
       └─ 生产环境：JSONRenderer
            │
            └─ stdlib logging（桥接）
                 └─ Loguru sink
                      ├─ stderr（实时输出，所有环境）
                      ├─ logs/ruoming_YYYY-MM-DD.log（所有级别，JSON）
                      └─ logs/ruoming_error_YYYY-MM-DD.log（仅 ERROR+）
```

- **`structlog`**：负责结构化处理、上下文变量绑定、格式渲染
- **`Loguru`**：负责文件轮转、压缩、保留策略，通过 stdlib logging 接收 structlog 输出
- 业务代码统一使用 `structlog.get_logger()` 获取 logger，不直接调用 Loguru

## 3. 日志文件

### 3.1 文件路径与策略

```
backend/logs/
├── ruoming_2026-06-25.log            # 全量日志（JSON，所有级别）
├── ruoming_2026-06-24.log.gz         # 昨日日志（自动 gzip 压缩）
├── ruoming_error_2026-06-25.log      # 错误日志（ERROR 及以上，快速定位）
└── ruoming_error_2026-06-24.log.gz
```

| 文件 | 级别 | 轮转 | 保留 | 压缩 |
|------|------|------|------|------|
| `ruoming_YYYY-MM-DD.log` | 全量（`LOG_LEVEL` 控制） | 每日 00:00 | 30 天 | gzip |
| `ruoming_error_YYYY-MM-DD.log` | ERROR 及以上 | 每日 00:00 | 30 天 | gzip |

> **所有环境均写文件**：开发环境同样持久化日志，便于本地溯源调试，不再区分生产/开发。

### 3.2 Docker 挂载

`deploy/docker-compose.yml` 中 `backend` 和 `celery_worker` 均挂载：

```yaml
volumes:
  - ../backend/logs:/app/logs   # 日志文件持久化到宿主机
```

容器重启或重建后日志文件不丢失，可直接在宿主机 `backend/logs/` 目录查看。

### 3.3 日志查看命令

```bash
# 查看今日实时日志（jq 格式化 JSON）
tail -f backend/logs/ruoming_$(date +%Y-%m-%d).log | jq .

# 查看今日所有错误
cat backend/logs/ruoming_error_$(date +%Y-%m-%d).log | jq .

# 按 trace_id 联查请求完整链路
grep "abc123" backend/logs/ruoming_$(date +%Y-%m-%d).log | jq .

# 查看历史压缩日志
zcat backend/logs/ruoming_2026-06-20.log.gz | jq .
```

## 4. 请求上下文追踪（trace_id）

每个请求由 `RequestIDMiddleware` 生成唯一 `trace_id`，自动绑定到 `structlog` 上下文：

```
请求进入
  └─ RequestIDMiddleware
       ├─ 生成/传递 trace_id（优先取 X-Request-ID 请求头）
       ├─ structlog.contextvars.bind_contextvars(trace_id=..., user_id=..., tenant_id=...)
       └─ 响应头回传 X-Request-ID

整个请求链路（中间件 → 路由 → service → 任何 logger.xxx() 调用）
  └─ 所有日志自动携带 trace_id
```

所有响应体也包含 `trace_id` 字段：

```json
{
  "code": 500,
  "message": "服务器内部错误",
  "data": null,
  "trace_id": "a1b2c3d4-..."
}
```

**trace_id 联查**：前端看到报错后，复制 trace_id，在日志文件中 `grep` 即可找到该请求的完整服务端日志链路。

## 5. 请求访问日志中间件

`RequestLoggingMiddleware` 记录每个请求的访问日志，同时写审计日志：

```python
logger.info/warning(
    "http_request",
    method=method,
    path=path,
    status_code=status_code,
    elapsed_ms=elapsed_ms,
    client_ip=request_ip,
    user_agent=user_agent,
    # trace_id 由 contextvars 自动注入
)
```

- `status_code >= 400` 时使用 `warning` 级别
- 未捕获异常使用 `logger.exception` 记录完整堆栈

### 审计日志写入策略

并非所有请求都记录审计日志（避免日志爆炸）：

| 条件 | 是否记录 |
|------|---------|
| `POST / PUT / DELETE / PATCH`（写操作） | ✅ 必须记录 |
| `GET` + 路径含数字 ID（详情查询） | ✅ 记录 |
| `GET` + 敏感资源（users/roles/permissions/tenants/configs/api-keys） | ✅ 记录 |
| `GET` + 含 export/download 关键词 | ✅ 记录 |
| `GET` + 普通列表查询 | ❌ 不记录 |

## 6. 审计日志（数据库）

### 6.1 数据库表 `sys_audit_log`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL | 主键 |
| `tenant_id` | BIGINT | 租户 ID |
| `user_id` | BIGINT | 操作用户 ID |
| `username` | VARCHAR | 操作用户名 |
| `event_type` | VARCHAR(64) | 事件类型（`method.path` 形式） |
| `module` | VARCHAR | 模块（路径第二段） |
| `action` | VARCHAR | HTTP 方法小写 |
| `resource_type` | VARCHAR | 资源类型（路径第三段） |
| `resource_id` | VARCHAR | 资源 ID |
| `status` | SMALLINT | 1=成功 0=失败 |
| `error_msg` | TEXT | 失败原因 |
| `request_ip` | VARCHAR | 客户端 IP |
| `browser` / `os` / `device` | VARCHAR | UA 解析结果 |
| `trace_id` | VARCHAR | 请求追踪 ID，可联查文件日志 |
| `path` | VARCHAR | 请求路径 |
| `method` | VARCHAR | HTTP 方法 |
| `created_at` | TIMESTAMPTZ | 创建时间 |

### 6.2 查询 API

```
GET /api/v1/audit/logs
  ?username=     用户名（模糊匹配）
  ?action=       操作动作（如：post、delete）
  ?resource_type= 资源类型（如：users、roles）
  ?status=       状态：1=成功 0=失败
  ?start_time=   开始日期（YYYY-MM-DD）
  ?end_time=     结束日期（YYYY-MM-DD）
  &page=&page_size=

GET /api/v1/audit/login-logs
  ?user_id=
  &page=&page_size=
```

## 7. 前端接口错误诊断面板

### 7.1 设计目标

后端日志记录的是"服务端视角"——请求到达服务器后的完整链路。但以下场景后端无法感知：

- 网络断开、DNS 失败、请求根本未发出
- 开发者/管理员不登录服务器、只在前端页面排查问题
- 需要快速获取 trace_id 再去日志文件联查

前端错误诊断面板补全"用户侧视角"，两者通过 `trace_id` 连接。

### 7.2 实现方式

**错误记录 Store（`src/store/errorLog.ts`）**

Pinia store，最多保存 200 条错误，页面关闭后清空：

```typescript
interface ErrorLogItem {
  id: string
  time: string
  status: number          // HTTP 状态码；业务错误时为 200
  code?: number           // 后端业务错误码
  method: string          // GET / POST / ...
  url: string             // 接口路径
  message: string         // 错误信息
  traceId?: string        // 后端 trace_id，用于日志文件联查
  responseSnippet?: string // 响应数据快照（截断至 300 字符）
}
```

**自动捕获（`src/utils/request.ts`）**

Axios 响应拦截器自动将以下情况写入 store：

| 触发条件 | status 值 |
|---------|----------|
| 业务错误（HTTP 200 但 `code ≠ 200/201`） | `200` |
| 网络断开/请求未发出 | `0` |
| 403 权限不足 | `403` |
| 429 限流 | `429` |
| 5xx 服务器错误 | `5xx` |
| 其他 4xx | 实际状态码 |

**ErrorLogDrawer 组件（`src/layouts/components/ErrorLogDrawer.vue`）**

集成在顶部 Header 右侧：

- 有未读错误时，Warning 图标变红并显示角标计数
- 点击打开抽屉，展示错误列表（时间、方法、路径、状态码、错误信息）
- 支持一键复制 `trace_id`，粘贴到服务端日志文件中 `grep` 联查
- 可展开查看原始响应快照
- 支持清空所有记录

### 7.3 后端日志联查流程

```
前端报错（红色 Warning 图标）
  └─ 打开错误面板
       └─ 找到目标错误，复制 TraceID
            └─ 服务端执行：
                 grep "<trace_id>" backend/logs/ruoming_$(date +%Y-%m-%d).log | jq .
                 # 或查错误日志
                 grep "<trace_id>" backend/logs/ruoming_error_$(date +%Y-%m-%d).log | jq .
```

## 8. 环境配置

`.env.development` / `.env.production` 相关配置项：

```ini
# 日志级别：DEBUG / INFO / WARNING / ERROR
LOG_LEVEL=INFO

# 是否输出 JSON 格式日志（文件日志始终为 JSON；此项控制 stderr 输出格式）
# true = 生产 JSON，false = 开发彩色可读
LOG_JSON=false
```
