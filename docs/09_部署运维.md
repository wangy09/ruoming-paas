# 09 部署运维

## 0. 运维脚本概览

项目在 `scripts/` 目录下提供了一系列运维脚本，覆盖日常运维的核心场景：

| 脚本 | 用途 | 适用场景 |
|------|------|----------|
| `start.sh` | 首次部署、日常启停 | 开发/生产环境启动、停止、查看状态和日志 |
| `deploy.sh` | 版本发布与灰度 | 生产环境版本部署、回滚、灰度发布 |
| `db_backup.sh` | 数据库备份与恢复 | PostgreSQL 定时备份、按需恢复 |
| `log_rotate.sh` | 日志轮转与清理 | 日志按大小轮转、压缩、过期清理 |
| `docker-restart.sh` | 强制重置环境 | 开发时修改数据库模型后的全量重建 |

## 1. Docker Compose（开发/测试环境）

开发环境使用 `deploy/docker-compose.yml`，包含热重载功能：

## 4. Nginx 配置

生产环境 Nginx 配置位于 `deploy/nginx/nginx.prod.conf`：

```nginx
upstream ruoming_backend {
    least_conn;
    server backend:8000 max_fails=3 fail_timeout=30s;
    keepalive 32;
}

server {
    listen 80;
    server_name _;

    client_max_body_size 100M;

    gzip on;
    gzip_types text/plain text/css application/json application/javascript;

    # 前端静态资源
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
        location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
    }

    # API 代理
    location /api/ {
        proxy_pass http://ruoming_backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_buffering off;
        proxy_read_timeout 120s;
    }

    # SSE 流式接口（AI 对话）
    location ~* /api/v1/ai/.*/stream {
        proxy_pass http://ruoming_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 300s;
        proxy_buffering off;
        add_header X-Accel-Buffering no;
    }
}
```

### SSL 配置（可选）

如需启用 HTTPS，在 Nginx 配置中添加：

```nginx
server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-RSA-AES256-GCM-SHA512:DHE-RSA-AES256-GCM-SHA512:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES256-GCM-SHA384;

    # ... 其余配置同上
}

# HTTP 重定向到 HTTPS
server {
    listen 80;
    server_name your-domain.com;
    return 301 https://$server_name$request_uri;
}
```

### 宿主机 Nginx 反向代理（可选）

> **适用场景**：当宿主机已安装 nginx 并占用 80/443 端口时，Docker nginx 改为只监听本地端口，由宿主机 nginx 反向代理。

**步骤 1：修改 Docker Compose 端口配置**

```yaml
# deploy/docker-compose.prod.yml
nginx:
  ports:
    - "127.0.0.1:8080:80"   # 只绑定本地，不暴露到公网
```

**步骤 2：配置宿主机 Nginx**

在宿主机 `/etc/nginx/conf.d/` 下新建配置文件：

```nginx
# /etc/nginx/conf.d/paas.conf
server {
    listen 80;
    server_name your-domain.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```bash
nginx -t && nginx -s reload
```

## 5. 数据库初始化

若茗 PaaS 采用**统一两步建表流程**，开发和生产环境保持一致：

| 步骤 | 命令 | 说明 |
|------|------|------|
| ① 建表结构 | `recreate_tables.py` | 非破坏式，CREATE IF NOT EXISTS |
| ② 写入种子数据 | `init_data.py` | 管理员、角色、权限、字典、计划任务 |
| ③ 写入 Agent 数据 | `seed_agents.py` | 内置 Agent，幂等可重复执行 |

### 首次部署（生产环境）

```bash
cd /opt/RuoMingPaas/deploy

# ① 非破坏式建表（跳过已存在的表）
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/recreate_tables.py

# ② 初始化基础数据（管理员 / 角色 / 权限 / 字典 / 计划任务）
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/init_data.py

# ③ 初始化 Agent 种子数据
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/seed_agents.py
```

成功输出示例：

```
✅ 若茗 PaaS 初始化完成！
   超管账号: admin
   超管密码: ruoming@2026
   API 文档: http://localhost:8000/api/docs
```

### 首次部署（开发环境）

```bash
cd deploy

# ① 建表
docker compose exec backend python /app/scripts/recreate_tables.py

# ② 种子数据
docker compose exec backend python /app/scripts/init_data.py

# ③ Agent 数据
docker compose exec backend python /app/scripts/seed_agents.py
```

### 重置数据库（仅开发环境，数据全清）

> ⚠️ **此操作会删除所有表和数据，仅在开发环境使用！**

```bash
cd deploy
docker compose exec backend python /app/scripts/recreate_tables.py --force
docker compose exec backend python /app/scripts/init_data.py
docker compose exec backend python /app/scripts/seed_agents.py
```

### 补建缺失表（不清数据）

当新模块上线后只需补建表，不需要重置所有数据：

```bash
# 生产环境
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/recreate_tables.py

# 开发环境
docker compose exec backend python /app/scripts/recreate_tables.py
```

`recreate_tables.py` 默认使用 `CREATE TABLE IF NOT EXISTS`，不会影响已有数据。

### 验证初始化数据

```bash
cd /opt/RuoMingPaas/deploy
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm -T backend python - <<'PY'
import asyncio
from sqlalchemy import text
from app.database import AsyncSessionFactory

async def main():
    async with AsyncSessionFactory() as session:
        r = await session.execute(text("SELECT username FROM sys_user ORDER BY id LIMIT 5"))
        print("用户:", [row[0] for row in r.fetchall()])
        r2 = await session.execute(text("SELECT name FROM ai_agent WHERE is_deleted = false ORDER BY id"))
        print("Agent:", [row[0] for row in r2.fetchall()])

asyncio.run(main())
PY
```

输出中包含 `admin` 且有内置 Agent（`闲聊助手`、`专业分析师` 等）即为成功。

> 如果初始化时提示未找到可用模型配置，Agent 仍会创建，但 `model_config_id` 为空。后续需要登录前端，在「模型管理」中配置模型后，再到「Agent 管理」里绑定模型。

## 8. 备份与恢复

### 使用 db_backup.sh 脚本（推荐）

项目提供了 `scripts/db_backup.sh` 脚本，支持自动轮转、压缩和 Webhook 通知。

**注意**：脚本不再硬编码数据库密码，必须通过环境变量 `DB_PASSWORD` 显式指定。

```bash
# 立即备份
DB_PASSWORD=<密码> bash scripts/db_backup.sh

# 指定备份目录
DB_PASSWORD=<密码> BACKUP_DIR=/data/backups bash scripts/db_backup.sh

# 使用 zstd 压缩（默认 gzip）
DB_PASSWORD=<密码> BACKUP_COMPRESS=zstd bash scripts/db_backup.sh

# 列出可用备份
bash scripts/db_backup.sh --list

# 从备份恢复（⚠️ 会清空现有数据，需输入 YES 确认）
DB_PASSWORD=<密码> bash scripts/db_backup.sh --restore /path/to/backup.sql.gz
```

**配合 crontab 定时备份**（每天凌晨 3 点执行）：

```bash
# 编辑 crontab
crontab -e

# 添加以下行（确保 DB_PASSWORD 安全存储在 .env 或其他安全位置）
0 3 * * * DB_PASSWORD=<密码> DB_HOST=localhost DB_NAME=ruoming_prod /opt/RuoMingPaas/scripts/db_backup.sh
```

**配置 Webhook 通知**（备份完成后自动通知）：

```bash
NOTIFY_WEBHOOK=https://hooks.example.com/webhook \
DB_PASSWORD=<密码> \
bash scripts/db_backup.sh
```

### 手动备份方式

```bash
# 创建备份目录
mkdir -p /opt/RuoMingPaas/deploy/postgres-backup

# 备份数据库
docker exec ruoming_postgres pg_dump -U ruoming ruoming_prod > /opt/RuoMingPaas/deploy/postgres-backup/backup-$(date +%Y%m%d-%H%M%S).sql
```

### 手动恢复方式

```bash
# 停止后端服务
docker compose --env-file .env.production -f docker-compose.prod.yml stop backend celery_worker task_scheduler

# 恢复数据库
docker exec -i ruoming_postgres psql -U ruoming ruoming_prod < /path/to/backup.sql

# 重启服务
docker compose --env-file .env.production -f docker-compose.prod.yml up -d
```

### Redis 备份

```bash
# Redis RDB 备份（Redis 已配置 appendonly yes）
docker exec ruoming_redis redis-cli -a <REDIS_PASSWORD> SAVE
```

## 9. 日志轮转与清理

### 使用 log_rotate.sh 脚本

项目提供了 `scripts/log_rotate.sh` 脚本，自动处理日志文件的轮转、压缩和过期清理。

```bash
# 立即执行日志轮转（默认：超过 100MB 的日志文件被轮转，30 天以上的日志被清理）
bash scripts/log_rotate.sh

# 仅检查日志状态，不执行轮转
bash scripts/log_rotate.sh --check

# 自定义参数
MAX_LOG_SIZE_MB=50 \        # 超过 50MB 轮转
MAX_LOG_AGE_DAYS=14 \       # 清理 14 天前的日志
LOG_DIR=/var/log/ruoming \  # 指定日志目录
bash scripts/log_rotate.sh
```

**配合 crontab 每天凌晨 2 点执行**：

```bash
crontab -e
0 2 * * * /opt/RuoMingPaas/scripts/log_rotate.sh
```

**轮转规则**：
- 单个 `.log` 文件超过 `MAX_LOG_SIZE_MB`（默认 100MB）时自动轮转
- 轮转后的日志被 gzip 压缩存储
- 超过 `MAX_LOG_AGE_DAYS`（默认 30 天）的旧日志自动删除

## 10. 版本发布与灰度

### 使用 deploy.sh 脚本

生产环境版本迭代使用 `scripts/deploy.sh`，支持版本部署、一键回滚和灰度发布。

```bash
# 部署指定版本（自动构建、替换、健康检查、失败回滚）
bash scripts/deploy.sh deploy v2.1.0

# 查看当前版本和部署状态
bash scripts/deploy.sh status

# 一键回滚到上一版本
bash scripts/deploy.sh rollback
```

### 灰度发布

灰度发布基于 Nginx Cookie 分流，逐步验证新版本稳定性：

```bash
# 启动灰度发布（30% 流量走新版本）
bash scripts/deploy.sh canary 30

# 生成灰度配置后，手动重新加载 Nginx
nginx -s reload

# 测试完成后，扩大灰度比例或全量发布
bash scripts/deploy.sh canary 50   # 扩大到 50%
bash scripts/deploy.sh deploy v2.1.0  # 全量发布
```

**灰度测试方法**：设置浏览器 Cookie `canary=1` 即可将该请求路由到灰度版本。

### 发布流程

1. 使用 `deploy.sh deploy <version>` 部署新版本
2. 自动健康检查通过则部署成功，失败则自动回滚
3. 建议先用 `canary` 灰度验证，确认无误后再全量发布
4. 回滚使用 `rollback`，可快速恢复到上一版本
5. 旧版本镜像自动清理（保留最近 5 个版本）

## 11. 演示模式配置

若茗 PaaS 支持演示模式，用于在公开环境中限制写操作，防止用户误修改数据。

### 默认行为

`DEMO_MODE` 默认为 `False`，即默认允许完整操作。需要演示模式时通过环境变量显式启用：

```bash
# 启用演示模式
DEMO_MODE=true

# 或在 .env 中配置
DEMO_MODE=true
```

### 演示模式限制

启用演示模式后：
- **写操作被禁止**：所有 `POST`、`PUT`、`DELETE`、`PATCH` 请求返回 403
- **读操作正常**：所有查询、浏览功能不受影响
- **白名单接口放行**：登录、刷新 Token、健康检查、公开配置等接口不受限制

### 前端 UI 提示

启用演示模式后，前端右下角会显示红色徽章，提示当前处于演示模式。

```json
  "status": "ok",
  "app": "RuoMing PaaS",
  "version": "2.1.0",

  "uptime": "5d 3h 20m"

```

### 详细健康检查（Readiness）

```bash
curl http://localhost:8000/api/health/detail
```

返回所有依赖组件的状态：

```json
{
  "status": "ok",
  "checks": {
    "database": { "status": "ok", "message": "PostgreSQL 连接正常 (12ms)" },
    "redis": { "status": "ok", "message": "Redis PONG (3ms)" },
    "disk": { "status": "warning", "message": "磁盘使用 85.2%，剩余 12.5GB" }
  },
  "duration_ms": 18
```

**监控集成**：可将健康检查接口接入 Prometheus、Grafana 或云服务商监控，实现自动告警。

## 13. 性能优化建议

### 资源配置

| 服务器规格 | 建议配置 |
|-----------|----------|
| 2核2G | 后端单实例，内存限制 768M |
| 4核4G | 后端单实例，内存限制 1536M |
| 8核8G+ | 后端多实例，可启用容器编排 |

### 前端构建优化

#### 问题：`npm run build` 卡死或服务器内存耗尽

**原因**：`vue-tsc` 类型检查遇到 TS 错误会卡住；Node.js 默认内存限制在低内存服务器上不够用。

**解决**：修改 `frontend/Dockerfile`，跳过 vue-tsc，限制内存：

```dockerfile
# 将原来的
RUN npm run build
# 改为
RUN NODE_OPTIONS="--max-old-space-size=1024" npx vite build
```

低配服务器上建议按服务顺序构建，避免后端和前端同时构建抢占内存：

```bash
cd /opt/RuoMingPaas/deploy
docker compose --env-file .env.production -f docker-compose.prod.yml build --no-cache backend
docker compose --env-file .env.production -f docker-compose.prod.yml build --no-cache frontend-builder
docker compose --env-file .env.production -f docker-compose.prod.yml up -d
```

如果服务器只有 2G 内存且仍然 OOM，建议临时增加 swap 后再构建，或在本地/CI 构建镜像后推送到服务器运行。

#### 问题：`npx vite build` 报 `vite: Permission denied`

**原因**：前端构建上下文中包含宿主机的 `frontend/node_modules`，`COPY . .` 时覆盖了镜像内 `npm ci` 安装的依赖，导致 `node_modules/.bin/vite` 权限或平台依赖不正确。

**解决**：确保 `frontend/.dockerignore` 中排除以下目录和文件：

```text
node_modules
dist
.env
.env.*
```

服务器上如已经存在旧的构建缓存，可重新构建前端镜像：

```bash
cd /opt/RuoMingPaas/deploy
docker compose --env-file .env.production -f docker-compose.prod.yml build --no-cache frontend-builder
docker compose --env-file .env.production -f docker-compose.prod.yml up -d frontend-builder nginx
```

## 10. 常见问题

### 服务启动失败

```bash
# 查看容器状态
docker compose --env-file .env.production -f docker-compose.prod.yml ps

# 查看详细日志
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=50 backend
```

### 数据库连接失败

```bash
# 检查数据库容器是否启动
docker exec ruoming_postgres pg_isready -U ruoming

# 检查数据库日志
docker compose --env-file .env.production -f docker-compose.prod.yml logs postgres
```

### 前端页面空白

```bash
# 检查后端健康
curl http://localhost:8000/api/health

# 检查前端构建是否成功
docker compose --env-file .env.production -f docker-compose.prod.yml logs frontend-builder
```

### 端口冲突

修改 `deploy/docker-compose.yml`（开发环境）或 `deploy/docker-compose.prod.yml`（生产环境）中的端口映射。

### PostgreSQL 密码认证失败

**现象**：`asyncpg: password authentication failed for user "ruoming"`

**原因**：Docker volume 中存有旧密码初始化的数据，修改密码后不生效。

**解决**：

```bash
# 停止服务
docker compose --env-file .env.production -f docker-compose.prod.yml down

# 删除旧 volume
docker volume rm deploy_postgres_data  # 或对应的 volume 名

# 重新启动
docker compose --env-file .env.production -f docker-compose.prod.yml up -d
```

### Nginx 容器反复重启

**现象**：`docker compose ps` 显示 nginx 状态为 `Restarting`

**原因**：nginx 配置引用了不存在的 SSL 证书文件。

**解决**：改为纯 HTTP 配置，或先提供证书文件再启用 HTTPS。

### 环境变量未加载（POSTGRES_USER 为空）

**现象**：启动时报 `required variable POSTGRES_USER is not set`

**原因**：`.env.production` 文件没有被正确加载。

**解决**：确保 `docker-compose.prod.yml` 中所有需要环境变量的服务都配置了 `env_file`：

```yaml
env_file:
  - .env.production
```

### 初始化时报 `relation "xxx" does not exist`

**现象**：`asyncpg.exceptions.UndefinedTableError: relation "sys_user" does not exist`（或其他表名）

**原因**：数据库结构尚未创建，或新模块的模型未注册到 `_import_models_for_metadata()`。

**解决**：执行非破坏式建表，再初始化种子数据：

```bash
cd /opt/RuoMingPaas/deploy
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/recreate_tables.py
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/init_data.py
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/seed_agents.py
```

### `init_data.py` 事务中断

**现象**：`asyncpg.exceptions.InFailedSQLTransactionError`

**原因**：`_write_history` 方法写入 `sys_config_history` 表，但该表不存在，导致 asyncpg 事务进入 aborted 状态。

**解决**：重新执行建表：

```bash
cd /opt/RuoMingPaas/deploy
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python /app/scripts/recreate_tables.py
```

### 新建模块后表不存在

**原因**：每新增一个业务模块，必须在 `backend/app/database.py` 的 `_import_models_for_metadata()` 函数中手动注册模型，SQLAlchemy 才能感知并建表。

**规范**：新建模块时，同步在 `_import_models_for_metadata()` 末尾追加导入：

```python
# backend/app/database.py  →  _import_models_for_metadata()
from app.modules.your_module.models import YourModel  # noqa: F401
```

追加后，执行一次 `recreate_tables.py` 即可补建缺失的表，不影响已有数据。
