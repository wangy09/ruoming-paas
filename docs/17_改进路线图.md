# 17 改进路线图

> **原则**：第一版不求大而全，优先保稳定、降成本、低改动量。  
> 改动以"改一处、不引入新组件、上下兼容"为首要标准。

---

## 阶段划分总览

| 阶段 | 周期 | 主题 | 核心目标 |
|------|------|------|---------|
| **Phase 1** | 1-2 个月 | 稳定基础 | 防雪崩、降 AI 成本、补审计 |
| **Phase 2** | 2-4 个月 | 企业适配 | 多租户隔离精细化、全链路安全 |
| **Phase 3** | 4-6 个月 | 扩展生态 | 微服务拆分、可观测性完善 |

## Phase 1：稳定基础（1-2 个月）

> **目标**：把最容易引发线上故障的短板补上，改动小、收益大。

### 1.1 LLM 熔断 + 自动降级

**背景**：主力模型（追鹿）故障时，所有 AI 请求会直接报错，可能连带影响前端页面。

**方案**：在 `LLMService.chat()` 内加轻量三状态熔断器，不引入任何新库，使用 `tenacity` 重试 + Redis 状态标记。

```
状态机：CLOSED（正常）→ OPEN（熔断）→ HALF_OPEN（探测）

触发条件：
  - 连续 5 次调用失败 → 切换到 OPEN 状态，60 秒内直接拒绝
  - 60 秒后进入 HALF_OPEN，允许 1 次试探请求
  - 试探成功 → 回到 CLOSED；试探失败 → 重置 60 秒计时

降级策略（按租户配置）：
  主力模型失败 → 自动切换到 ai_model_config 中 is_fallback=true 的备用模型
  备用模型也失败 → 返回友好错误消息，不抛出 500
```

**涉及改动**：
- `ai_model_config` 表新增 `is_fallback BOOLEAN DEFAULT FALSE` 字段
- `LLMService.chat()` 加熔断包装层（~50 行）
- Redis key：`llm:circuit:{model_config_id}:state`

**不做**：Resilience4j、Hystrix 等重型 Java 生态库，Python 不适用。

---

### 1.2 AI 请求异步化（背压控制）

**背景**：LLM 调用单次耗时 5-30 秒，高并发时同步调用会拖垮工作线程。

**方案**：利用**已有的 `arq` 任务队列**，将耗时 AI 请求改为异步模式，无需引入 RabbitMQ。

```
同步模式（当前）：
  POST /ai/agent/run → 等待 LLM 返回 → 响应（最长阻塞 30s）

异步模式（改造后）：
  POST /ai/agent/run → 立即返回 task_id（< 100ms）
  客户端通过 SSE / 轮询 GET /ai/tasks/{task_id} 获取进度和结果

并发控制：
  arq worker 配置 max_jobs=20（可按租户分桶限制）
  超出则排队等待，不丢请求也不雪崩
```

**涉及改动**：
- 在已有 `arq` Worker 注册 AI 任务函数
- 前端 SDK 封装 task 轮询逻辑（或 SSE 订阅）
- 接口保持向后兼容（同步模式仍可用，异步模式为新增路径）

### 1.3 语义缓存（Semantic Cache）

**背景**：相同或相近的 Prompt 重复请求会重复消耗 Token，增加成本。

**方案**：在 `LLMService` 加一层 Redis Hash 缓存，key = `hash(model_id + messages_text)`。

```
缓存策略：
  - TTL 可配置（默认 1 小时，创意类场景建议关闭）
  - 通过 config_center 的 ai.cache.enabled / ai.cache.ttl 按租户控制
  - 命中时跳过 LLM 调用，直接返回缓存结果并记录 ai_call_log（status=cached）

适用场景：
  - RAG 检索结果相对固定的知识库问答（高命中率）
  - 重复的系统 Prompt + 固定用户输入（如批量数据处理）

不适用场景：
  - 对话历史参与上下文的多轮对话（每轮 messages 不同，缓存无意义）
  - creative 场景（故意需要随机性）
```

**涉及改动**：
- `LLMService.chat()` 加缓存前置检查（~20 行）
- `ai_call_log.status` 新增 `cached` 枚举值

---

### 1.4 配置中心变更历史

**背景**：租户配置变更无记录，出问题无法溯源，合规要求必备。

**方案**：新增 `sys_config_history` 表，在 `ConfigCenterService.set()` 写入时自动记录。

```sql
CREATE TABLE sys_config_history (
    id          BIGSERIAL PRIMARY KEY,
    config_key  VARCHAR(256) NOT NULL,
    scope_type  VARCHAR(20) NOT NULL,    -- global/tenant/app/user
    scope_id    BIGINT,
    old_value   TEXT,
    new_value   TEXT,
    changed_by  BIGINT,
    changed_at  TIMESTAMPTZ DEFAULT NOW(),
    remark      TEXT
);
```

**涉及改动**：
- 新增上述表（一次 Alembic 迁移）
- `ConfigCenterService.set()` 改写时异步写入历史（非阻塞）
- 管理后台增加「配置变更历史」查询接口

---

### 1.5 PostgreSQL 读写分离预备

**背景**：当前 ORM 层只有单个连接池，主从部署后无法自动分流。

**方案**：ORM 层拆分为 `write_session` 和 `read_session` 两个依赖注入工厂，生产环境一键切换。

```python
# core/database.py 改造
# 开发/测试环境：read_engine = write_engine（同一个）
# 生产环境：通过环境变量 DATABASE_REPLICA_URL 指向只读副本

async def get_write_session() -> AsyncSession: ...
async def get_read_session() -> AsyncSession: ...
```

**涉及改动**：
- `core/database.py` 新增 replica 连接池（READ_DB_URL 未配置时退回主库，向后兼容）
- `TenantAwareRepository` 基类新增 `read_db` 可选参数
- 不修改现有业务代码，Repository 层改一处基类即可

---

### 1.6 Redis 哨兵/集群模式预备

**背景**：单节点 Redis 是 SPoF（单点故障），生产不可接受。

**方案**：`core/redis.py` 支持三种模式，通过环境变量切换，不修改上层代码。

```python
# REDIS_MODE: standalone（默认）/ sentinel / cluster
# REDIS_SENTINEL_MASTER: mymaster
# REDIS_SENTINEL_HOSTS: 127.0.0.1:26379,127.0.0.1:26380

def create_redis_pool():
    match settings.REDIS_MODE:
        case "sentinel":
            return Sentinel(...).master_for(settings.REDIS_SENTINEL_MASTER)
        case "cluster":
            return RedisCluster(...)
        case _:
            return Redis.from_url(settings.REDIS_URL)
```

**涉及改动**：
- `core/redis.py` 改一处工厂函数（~30 行）
- Docker Compose 增加 sentinel 示例配置（`docker-compose.sentinel.yml`）
- 不修改任何使用 Redis 的业务代码

## Phase 2：企业适配（2-4 个月）

> **目标**：满足企业客户在安全、合规、多租户隔离方面的核心诉求。  
> 前提：Phase 1 完成后再启动。

### 2.1 多租户资源隔离精细化

**当前状态**：已有 `max_concurrent` 并发限制和 Token 日配额。

**Phase 2 补充**：

| 能力 | 方案 | 复杂度 |
|------|------|--------|
| **AI 调用按租户限速** | `rate_limit` 模块已有滑动窗口算法，扩展按 `tenant_id` 分桶的 AI 专属限速规则 | 低 |
| **数据库查询超时保护** | SQLAlchemy `execution_options(timeout=...)` 按接口设置查询超时，防止大查询拖垮主库 | 低 |
| **CPU/内存按租户监控** | Prometheus 指标增加 `tenant_id` label，Grafana 看板增加租户维度视图 | 中 |
| **独立实例部署模式** | 在 `sys_tenant` 新增 `deployment_mode: shared/dedicated` 字段，文档说明独立实例配置方法 | 中 |

### 2.2 全链路安全补强

**当前安全基线**（已有）：JWT 认证、bcrypt 密码、SQL 注入防护、文件上传安全。

**Phase 2 补充**：

| 能力 | 方案 |
|------|------|
| **敏感字段日志脱敏** | 实现 `@sensitive_field` 装饰器，手机号/邮箱在 structlog 输出时自动 mask（`138****8888`） |
| **RAG 文档权限细化** | `ai_knowledge_base_share` 表已设计，Phase 2 实现文档级权限（chunk 检索时过滤无权限文档）|
| **Prompt 内容审核** | 接入简单关键词过滤（敏感词库），生产环境可接入内容安全 API（可配置化，默认关闭） |
| **API 接口脱敏** | 响应体中的敏感字段（如手机号）自动脱敏，通过 Pydantic `field_serializer` 实现 |

### 2.4 Workflow 暂停/恢复能力

**当前状态**：`ai_workflow_run.status` 有 `pending/running/success/failed/timeout`。

**Phase 2 补充**：

```sql
-- ai_workflow_run.status 新增枚举值
-- paused（人工暂停）/ cancelled（主动取消）
-- 新增字段：
ALTER TABLE ai_workflow_run
    ADD COLUMN paused_at TIMESTAMPTZ,
    ADD COLUMN paused_reason TEXT,
    ADD COLUMN resume_input JSONB;  -- 恢复时可注入新的输入
```

新增接口：
```
POST /api/v1/ai/workflow/runs/{run_id}/pause    暂停运行中的工作流
POST /api/v1/ai/workflow/runs/{run_id}/resume   恢复暂停的工作流
POST /api/v1/ai/workflow/runs/{run_id}/retry    重试失败的工作流（从失败节点重新开始）
POST /api/v1/ai/workflow/runs/{run_id}/cancel   取消（不可恢复）
```

## Phase 3：扩展生态（4-6 个月）

> **前提**：Phase 1 + 2 稳定运行 1 个月以上，有实际用户反馈后再启动。  
> **注意**：Phase 3 的改动均为**较大架构变更**，需单独评估。

### 3.1 AI 专属可观测性

新增 Prometheus 指标（通过 `prometheus_fastapi_instrumentator` 扩展）：

| 指标 | 类型 | 说明 |
|------|------|------|
| `llm_call_total{status,model,tenant}` | Counter | LLM 调用总次数（成功/失败/缓存命中） |
| `llm_call_latency_seconds{model,tenant}` | Histogram | LLM 调用延迟分布（P50/P95/P99）|
| `llm_token_usage_total{model,tenant}` | Counter | Token 消耗总量 |
| `rag_recall_top_k_score{kb_id}` | Gauge | 最近 100 次检索的平均最高分（监控召回质量） |
| `workflow_run_duration_seconds{workflow_id}` | Histogram | 工作流执行耗时 |
| `circuit_breaker_state{model_config_id}` | Gauge | 熔断器状态（0=CLOSED, 1=OPEN, 2=HALF_OPEN）|

告警规则（Prometheus Alertmanager）：

```yaml
# 按 P0-P3 四级告警
- alert: LLMGatewayDown       # P0
  expr: llm_call_total{status="success"}[5m] == 0
  for: 2m
  annotations:
    summary: "AI 网关 5 分钟内无成功调用"

- alert: TenantTokenOverQuota  # P1
  expr: llm_token_usage_total{tenant="xxx"} > tenant_quota * 0.9
  annotations:
    summary: "租户 Token 使用量超 90%"
```

### 3.2 微服务拆分（慎重）

**当前建议**：保持**模块化单体（Modular Monolith）**，不拆微服务。

**何时考虑拆分**：
- 单进程内存/CPU 触顶，垂直扩容无效
- 不同模块发布频率差异极大（如 AI 网关每天发布，权限系统每月发布）
- 团队规模超过 20 人，模块间耦合导致协作摩擦

**拆分优先级（当时机成熟时）**：
1. `ai.llm` 网关（调用量最大、独立扩容价值最高）
2. `auth` 认证服务（跨系统复用需求）
3. `ai.knowledge` 知识库（向量计算资源密集）

**注意**：微服务拆分引入的分布式事务、服务间认证、网络延迟等问题，不亚于业务复杂度本身，慎重启动。

---

### 3.3 合规与数据保护

| 能力 | 依赖的前置条件 | 方案 |
|------|--------------|------|
| **审计日志不可篡改** | Phase 1 稳定 | OSS WORM（对象锁）策略，审计日志定期归档到对象存储，设置保留期限 |
| **数据脱敏/匿名化** | Phase 2 脱敏基础 | 在 `compliance` 模块实现 GDPR「删除权」：用户注销时触发异步任务，清理/匿名化所有个人数据 |
| **等保 2.0 适配** | — | 主要是文档和配置层面（日志留存 ≥ 6 个月、最小权限原则、安全扫描），无需大量代码改动 |

## 暂不采纳事项（明确排除）

以下建议在**当前阶段明确不做**，避免过度工程化：

| 建议 | 排除理由 |
|------|---------|
| 服务注册发现（Consul/Nacos）| Nginx 已满足，K8s 环境下 Service 天然解决；引入成本远超收益 |
| PostgreSQL Citus 分库分表 | 共享库+行级 RLS 可支撑数百万租户，过早优化 |
| 前端 SSR/SSG | 企业管理系统 SPA 足够，引入 Node 服务层破坏简单部署优势 |
| 插件市场 / 第三方 SDK | v4.0 生态版规划，当前连 v2.0 MVP 都未完成 |
| 区块链审计日志 | OSS WORM 策略满足合规要求，区块链无必要 |
| AI 内容水印/溯源 | 监管要求尚不清晰，技术方案不成熟 |
| 多云适配层 | 若茗是开发者底座，用户自选云；通用接口已有抽象 |
